솔버 설정과 시간 관리: Gurobi에 건 설정 여덟 가지

모형을 다 적었으면 남은 일은 model.optimize() 한 줄입니다. 그 한 줄이 제한 시간의 거의 전부를 쓰므로, 솔버가 그 시간을 어떻게 쓸지를 정하는 설정을 알아야 풀이를 다 이해한 것이 됩니다. 미리 말해 두면, tryAgain은 설정을 많이 건드리지 않았습니다. 이 장은 myalgorithm.cpp(152줄)를 읽으며 tryAgain이 바꾼 설정 하나하나가 무엇이고 왜 그렇게 했는지를 봅니다.

파라미터의 뜻과 기본값은 Gurobi 12.0 공식 문서의 파라미터 참조 페이지에서 확인한 것입니다. "왜 그렇게 했는지"는 발표자료에 적힌 것과 코드 주석에 있는 것만 사실로 적고, 나머지는 추측이라고 표시했습니다. 팀의 코드를 실행해 로그를 확인한 것은 없습니다.

1부 · solve() 한눈에

함수의 흐름

void solve(num_nodes, num_ports, fixed_cost, num_edges, edges,        // 입력 (자료형은 생략)
           num_demands, od_pairs, demands, time_limit,
           out_port_route_num, out_demand_indices, out_route_lengths, out_routes)   // 출력
{
    auto start_time = chrono::steady_clock::now();              // ① 시계 시작

    const double postprocessingTime = 2.0;                      // 해 복원에 남겨 둘 시간(초)
    const double Heur_proportion = 0.15;
    const double noRelThreshold = 10000;

    GRBEnv env = GRBEnv(true);  env.start();  GRBModel model(env);   // ② 환경과 빈 모형
    model.set(GRB_IntParam_OutputFlag, 0);
    model.set(GRB_DoubleParam_MIPGapAbs, 2 - TOL);
    model.set(GRB_IntParam_PoolSolutions, 1);
    model.set(GRB_IntParam_Method, 2);
    model.set(GRB_IntParam_Crossover, 0);

    // ③ C 배열 → 이웃 목록, 수요 표
    getBFSOrientation(nodeVec, positionVec);                    // ④ 높이 (5장)
    formulate(...);                                             // ⑤ 모형 (6장)

    // ⑥ 시간 배분
    const double IPComputationTime = time_limit - (지금까지 걸린 초) - postprocessingTime;
    model.set(GRB_DoubleParam_TimeLimit, IPComputationTime);
    model.set(GRB_DoubleParam_Heuristics, Heur_proportion);

    const int problemSize = num_nodes * num_ports * (num_ports-1) / 2;
    if (problemSize > noRelThreshold)                           // ⑦ 큰 문제이면
        model.set(GRB_DoubleParam_NoRelHeurTime, IPComputationTime);

    model.optimize();                                           // ⑧ 여기서 시간의 거의 전부를 쓴다
    get_solution(...);                                          // ⑨ 해 복원 (7장)
    std::copy(...);                                             // ⑩ 출력 배열에 복사
}

②의 「환경」(GRBEnv)은 Gurobi를 쓰기 위해 먼저 만들어야 하는 객체로, 라이선스를 확인하고 파라미터의 기본값을 들고 있습니다. GRBEnv(true)로 빈 환경을 만들고 start()로 시작한 뒤, 그 환경 위에 모형(GRBModel)을 만듭니다. model.set(파라미터, 값)이 설정을 바꾸는 호출이고 모두 여덟 번 나옵니다. 차례로 봅니다.

2부 · 설정 하나씩

MIPGapAbs = 2 − TOL: 짝수만 나오는 목적함수

4장에서 본 요령입니다. 목적함수 값이 띄엄띄엄하면, 상한과 하한의 차이가 그 간격보다 작아지는 순간 더 좋은 해가 없다는 것이 확정됩니다.

6장의 목적함수는 Σ 2·(F + dist(i))·xpqi입니다. F와 dist(i)가 정수이고 x가 0 또는 1이므로 모든 가능해의 목적함수 값은 짝수입니다. 지금 들고 있는 해의 값이 1,000이라면 더 좋은 해는 998 이하여야 합니다. 하한이 998.001을 넘어서면 그런 해는 없습니다. 그래서 "차이가 2 미만이면 멈춰라"가 안전합니다. 2에서 TOL(0.001)을 뺀 것은 "2 미만"을 수치 오차에 대해 조금 더 엄격하게 적용하려는 것으로 읽힙니다.

기본값 1e-10 그대로 두면 솔버는 차이가 사실상 0이 될 때까지 계속합니다. 4장의 트럭 예에서 봤듯이 마지막 남은 작은 차이를 메우려면 가지를 더 나눠야 하고, 문제에 따라서는 그 마무리에 긴 시간이 듭니다. 이 한 줄은 그 마무리를 생략하고 일찍 끝나게 해 줍니다. 대회 점수에는 실행 시간이 반영되지 않으니 점수를 올려 주지는 않지만, 잃는 것도 없습니다.

주석의 "odd circuit"에 대해. 이 줄의 주석은 "Set absolute MIP gap to 2, which is valid unless there is no odd circuit in the deck graph"입니다. 글자 그대로 읽으면 "홀수 순환이 없지 않은 한 유효하다"가 되어 뜻이 어색합니다. 모형의 목적함수는 그래프의 모양과 상관없이 항상 짝수이므로, 모형의 최적성을 판정하는 데에는 이 설정이 언제나 유효합니다. 아마도 6장에서 본 사실, 즉 홀수 순환이 없는 배에서만 모형의 비용이 실제 비용과 일치한다는 점을 가리키려던 주석이 부정어가 하나 꼬인 것으로 추측합니다. 추측일 뿐이고 주석의 의도를 확인할 방법은 없습니다.

한 가지 더 볼 것이 있습니다. 상대 gap MIPGap은 건드리지 않아 기본값 1e-4(0.01%)가 그대로입니다. Gurobi는 두 기준 중 하나만 충족해도 멈춥니다. 목적함수 값이 총비용이므로(LB를 빼지 않습니다), 총비용이 2만을 넘는 문제에서는 0.01%가 2보다 커져서 상대 기준이 먼저 걸립니다. 예를 들어 지금 해의 총비용이 100,000이면 상대 기준은 차이 10 미만입니다. 하한이 99,990을 조금 넘는 순간 솔버는 멈추는데, 그때 99,992, 99,994, 99,996, 99,998이라는 더 좋은 짝수 값 네 개가 아직 배제되지 않은 상태입니다.

이것은 드문 경우가 아닙니다. 6장의 공개 연습 문제 20개 가운데 18개는 LB만 해도 2만을 넘습니다(가장 작은 두 문제가 7,014와 13,259이고, 나머지는 24,557에서 668,003). 분지한계법 쪽으로 가는 14문제 중에서도 12문제가 그렇습니다. 이런 문제에서는 MIPGapAbs = 2보다 기본값인 상대 기준이 먼저 걸리므로, 솔버가 "최적"이라고 끝내도 모형의 진짜 최적보다 2에서 몇 단위 나쁜 해일 수 있습니다. 1장에서 봤듯이 이 대회는 1 차이로도 순위가 갈립니다. MIPGap을 0으로 주었다면 이 여지는 없었을 것입니다. 다만 이것이 실제 성적에 영향을 줬는지는 실행 로그가 없어 알 수 없습니다. 시간 안에 gap이 그만큼 좁혀지지 않았다면 어차피 상관없는 이야기이고, 큰 문제는 아래에서 볼 NoRel 쪽으로 가므로 하한 자체가 쓰이지 않습니다.

Heuristics = 0.15: 가능해 찾기에 세 배

Gurobi 문서의 설명은 "MIP 풀이 시간 중 휴리스틱에 쓰려는 비율"이고, 값을 키우면 가능해를 더 많이, 더 좋게 찾는 대신 하한이 올라가는 속도가 느려진다고 되어 있습니다. 기본 5%를 15%로 올렸습니다.

이유는 대회의 채점 방식에서 짐작할 수 있습니다. 점수는 제한 시간이 끝났을 때 들고 있는 해의 값으로만 매겨지고, 하한이 얼마나 좋은지는 점수와 무관합니다. 시간 안에 최적 증명까지 가지 못할 문제라면 상한 쪽에 시간을 더 쓰는 편이 유리합니다. 0.15라는 값을 어떻게 골랐는지는 자료에 없습니다.

Method = 2, Crossover = 0: 뿌리 완화를 배리어로

Method는 MIP에서 맨 처음의 LP(뿌리 완화)를 푸는 알고리듬을 정합니다. 기본값(자동)은 MIP의 뿌리 완화에 보통 쌍대 심플렉스를 고릅니다. tryAgain은 이것을 배리어(내부점법)로 고정했습니다. 4장에서 본 대로 배리어는 큰 LP에서 대체로 빠르고 여러 코어를 잘 씁니다. 발표자료 8쪽이 "모형의 크기가 커질수록 선형완화문제를 푸는 데 걸리는 계산적 부담이 커져"라고 적은 것과 같은 맥락으로, 뿌리의 LP를 빨리 끝내려는 설정으로 보입니다. Gurobi의 자동 설정도 큰 모형에서는 여러 알고리듬을 동시에 돌려 먼저 끝나는 것을 쓰는데, 그 경우 코어를 나눠 쓰게 됩니다. 배리어로 고정하면 코어를 배리어 하나에 몰아줍니다. 이 차이가 실제로 도움이 됐는지는 측정한 자료가 없습니다.

Crossover = 0은 배리어의 답을 꼭짓점 답으로 바꾸는 후처리를 끄는 설정입니다. 크로스오버는 큰 LP에서 배리어 본체만큼 시간이 걸리기도 하므로, 끄려 한 의도는 그 시간을 아끼는 것으로 짐작됩니다. 발표자료 16쪽도 "Barrier 알고리듬에서 crossover: 끔"이라고 적고 있습니다. 그런데 Gurobi 12 문서의 Crossover 항목에는 다음 단서가 붙어 있습니다.

문서의 단서. MIP의 뿌리 완화에서 크로스오버를 끄려면 Method와 NodeMethod(뿌리가 아닌 가지의 LP를 푸는 알고리듬)가 둘 다 배리어로 설정되어 있어야 한다고 되어 있습니다. 분지한계법은 꼭짓점 답(기저)에서 출발해야 가지들을 심플렉스로 이어 풀 수 있기 때문입니다. tryAgain의 코드는 NodeMethod를 설정하지 않습니다. 문서대로라면 Crossover = 0은 이 모형에서 효과가 없고 크로스오버는 그대로 수행될 것입니다. 실제 로그로 확인한 것은 아닙니다. (정말로 끄려면 NodeMethod도 배리어로 줘야 하는데, 그러면 모든 가지의 LP를 이어 풀기 없이 배리어로 처음부터 풀게 되어 분지한계법 전체가 느려질 수 있습니다.)

어느 쪽이든 해의 유효성과는 무관합니다. 뿌리의 LP를 푸는 데 걸리는 시간에만 영향을 줍니다.

NoRelHeurTime: 크면 분지한계법을 포기한다

const int problemSize = num_nodes * num_ports * (num_ports-1) / 2;   // x 변수의 수 (근사)
if (problemSize > noRelThreshold) model.set(GRB_DoubleParam_NoRelHeurTime, IPComputationTime);

4장에서 본 NoRel 휴리스틱입니다. LP 완화를 풀지 않고 가능해를 찾아 개선하는 Gurobi의 내장 휴리스틱이고, 뿌리 완화를 풀기 전에 주어진 시간만큼 돕니다. tryAgain은 그 시간을 솔버의 제한 시간 전체와 같게 줍니다. 문서의 설명대로 동작한다면 NoRel이 끝나는 순간 제한 시간도 끝나므로, 뿌리의 LP는 풀리지 않고 분지한계법은 시작도 하지 않을 것입니다. 발표자료 9쪽도 이 경우를 "전체 시간 동안 Gurobi의 noRel 휴리스틱 사용"이라고 적고 있습니다. (로그로 확인한 것은 아니므로, 이 장에서 NoRel 쪽의 동작에 대해 하는 말은 모두 이 전제 위에 있습니다.)

problemSize ≤ 10,000

Gurobi의 보통 흐름. 전처리 → 뿌리 완화(배리어) → 분지한계법. 휴리스틱 비중 15%. 차이가 2 미만이 되면 최적으로 끝.

problemSize > 10,000

제한 시간 내내 NoRel 휴리스틱. 하한은 사실상 없고 일찍 끝나지도 않습니다. Method, Crossover, Heuristics, MIPGapAbs는 쓰일 일이 없을 것입니다.

problemSize는 N × P(P−1)/2입니다. 주석은 "xpqi 변수의 수"라고 하는데 정확한 x의 수는 (N−1) × P(P−1)/2이므로 조금 큽니다. 기준 10,000을 넘는 노드 수는 항구 수에 따라 다음과 같습니다.

  • 예선에 제출한 알고리듬은 모든 문제에서 제한 시간 내내 NoRel 휴리스틱을 쓰는 것이었다.
  • 이와 별개로 팀이 개인적으로 실험해 보니, "하역 후 재적재가 없다고 가정하는" 모형(이 문서의 기호로는 z를 뺀 모형)을 Gurobi 기본 설정으로 풀면 예선 평가 문제 다섯 개 모두에서 1분 안에 최적해를 얻었고, 그 값은 대회에서 나온 가장 좋은 값과 같았다.

두 번째는 실험 결과의 소개이지 제출한 알고리듬이 아닙니다. (z가 없는 모형은 5장에서 본 "항상 가능해가 있다"는 보장이 없어서, 예시 문제처럼 임시 하역이 꼭 필요한 문제에서는 불능이 됩니다.) 본선 제출본에서 "작은 문제는 분지한계법"이라는 갈림이 추가된 것은 이 경험에서 나온 것으로 보입니다.

PoolSolutions = 1, OutputFlag = 0

Gurobi는 탐색 중에 찾은 해를 기본 10개까지 보관합니다(해 풀). 필요한 것은 가장 좋은 해 하나뿐이므로 1로 줄였습니다. 메모리와 관리 비용을 조금 아끼는 설정이고 탐색 자체는 바뀌지 않습니다. OutputFlag = 0은 로그를 끕니다. 코드에는 로그 파일을 열던 흔적이 주석으로 남아 있습니다(// ofstream log_file("log.txt");).

3부 · 시간

시간 배분

const double IPComputationTime = time_limit
    - chrono::duration_cast<chrono::seconds>(chrono::steady_clock::now() - start_time).count()
    - postprocessingTime;
model.set(GRB_DoubleParam_TimeLimit, IPComputationTime);
  • 경과 시간은 초 단위로 버림합니다. duration_cast<seconds>는 0.9초를 0으로 만듭니다. 그래서 준비에 걸린 시간이 최대 1초 가까이 덜 빠질 수 있고, 그만큼은 2초의 여유에서 나갑니다.
  • 시계는 C++ 함수에 들어온 뒤에 시작합니다. 대회가 재는 것은 Python의 algorithm() 전체입니다. .so를 불러오고 입력을 C 배열로 바꾸는 시간, 끝난 뒤 배열을 dict로 되돌리는 시간은 C++의 시계 밖에 있습니다. 이것도 2초의 여유로 감당합니다.
  • Gurobi는 제한 시간에 정확히 멈추지 않을 수 있습니다. 문서에 따르면 TimeLimit에 도달해도 즉시 멈추지 못해 실제 실행 시간이 조금 넘을 수 있습니다.

2초가 이 셋을 모두 덮기에 충분했는지는 결과가 말해 줍니다. 세 단계 29문제에서 tryAgain의 시간 초과 기록은 없습니다. 결선에서 가장 짧았던 제한 시간은 30초였고, 그 문제에서 솔버가 쓴 시간은 약 28초였을 것입니다.

항목상태의미
Threads설정 안 함 (기본 0 = 자동)문서에 따르면 자동 설정은 대체로 가상 프로세서 수만큼(최대 32) 스레드를 씁니다. 평가 서버는 16코어이고 대회는 CPU 사용을 4코어(400%)로 제한합니다. Gurobi가 서버에서 몇 개의 스레드를 띄웠는지, cpulimit의 제한 아래에서 어떻게 동작했는지는 알 수 없습니다. 4로 명시했다면 더 좋았을지도 확인할 방법이 없습니다.
초기해(MIP start)주지 않음5장의 "전부 내렸다 다시 싣기" 같은 뻔한 가능해를 솔버에 미리 넣어 주지 않습니다. 가능해 찾기는 전적으로 Gurobi의 휴리스틱에 맡깁니다.

Cuts주석 처리됨// model.set(GRB_IntParam_Cuts, 0); 절단평면을 끄는 실험을 했다가 되돌린 흔적으로 보입니다.

MIPFocus기본값 (0, 균형)탐색의 무게를 가능해 찾기, 최적 증명, 하한 개선 중 어디에 둘지 정하는 상위 스위치입니다. 건드리지 않았습니다.
Seed기본값솔버 내부 난수의 씨앗. 바꾸면 같은 모형도 탐색 경로가 달라집니다.

전체적으로 "모형을 잘 적고, 솔버는 거의 기본값으로" 쓴 풀이입니다. 바꾼 설정 여덟 가지 가운데 탐색의 성격을 바꾸는 것은 휴리스틱 비율과 NoRel 분기 두 가지 정도이고, 나머지는 시간 관리와 마무리에 관한 것입니다. 솔버 튜닝보다 정식화가 성패를 갈랐다는 뜻으로 읽을 수 있습니다.

4부 · 빌드와 배포

C++ 코드를 대회 서버에서 돌리기까지

1장에서 봤듯이 대회의 진입점은 Python이고, 서버는 컴파일을 해 주지 않습니다. tryAgain은 Ubuntu에서 미리 만든 공유 라이브러리를 함께 제출하고 Python의 ctypes로 부릅니다.

# build.sh의 핵심
g++ -std=c++17 -O3 -fPIC -I${GUROBI_HOME}/include -c function.cpp   -o function.o
g++ -std=c++17 -O3 -fPIC -I${GUROBI_HOME}/include -c myalgorithm.cpp -o myalgorithm.o
g++ -shared -Wl,-soname,lib_myalgorithm.so -o lib_myalgorithm.so function.o myalgorithm.o \
    -L${GUROBI_HOME}/lib -lgurobi_c++ -lgurobi120
부분뜻
-std=c++17 -O3, -cC++17 문법으로, 최적화를 켜고, 소스 파일 하나를 목적 파일(.o)로 컴파일합니다.
-I…/include, -L…/libGurobi의 헤더 파일과 라이브러리 파일이 있는 폴더를 알려 줍니다. GUROBI_HOME은 Gurobi를 설치한 폴더를 가리키는 환경 변수입니다.
-fPIC, -shared실행 파일이 아니라 다른 프로그램이 불러 쓰는 공유 라이브러리(.so)를 만듭니다.
-Wl,-soname,…만들어지는 라이브러리 안에 자기 이름을 기록해 둡니다.
-lgurobi_c++Gurobi의 C++ 인터페이스. 정적 라이브러리라서 그 코드가 lib_myalgorithm.so 안에 복사되어 들어갑니다.
-lgurobi120Gurobi 12.0 본체(libgurobi120.so). 공유 라이브러리라서 복사되지 않고 "실행할 때 이 파일이 필요하다"는 표시만 남습니다. 따라서 실행하는 컴퓨터(평가 서버)에 Gurobi 12.0이 설치되어 있어야 합니다.
extern "C" (소스 쪽)C++ 컴파일러가 함수 이름을 바꾸지 않게 해서 ctypes가 solve라는 이름으로 찾을 수 있게 합니다.
 
# myalgorithm.py
cpp_lib = ctypes.CDLL('./lib_myalgorithm.so')
cpp_lib.solve.argtypes = [ctypes.c_int, ..., ctypes.POINTER(ctypes.c_int), ...]
c_edges = (ctypes.c_int * len(edges_flat))(*edges_flat)      # Python list → C 정수 배열
cpp_lib.solve(num_nodes, num_ports, fixed_cost, num_edges, c_edges, ..., timelimit, c_out_..., ...)

확인한 것과 확인하지 못한 것을 구분해 적습니다.

  • 확인: 제출 압축 파일에는 json.hpp가 없습니다. Base.hpp가 #include "./json.hpp"를 하고 있어서, 받은 소스 그대로는 이 헤더(nlohmann/json)를 따로 구해 넣어야 컴파일됩니다. 코드 본문은 JSON을 쓰지 않습니다.
  • 확인: 동봉된 lib_myalgorithm.so는 Linux용이라 macOS나 Windows에서는 불러올 수 없습니다.
  • 확인하지 못함: 평가 서버의 Gurobi 설치와 라이선스. 대회 환경에는 gurobipy 12.0.1이 있었고 Gurobi가 후원사였습니다. C++ 라이브러리를 직접 링크한 이 .so가 서버에서 libgurobi120.so와 라이선스를 어떻게 찾았는지는 자료에 없습니다. 결과가 정상적으로 나왔으니 찾기는 했습니다.
  • 확인하지 못함: gurobipy로 Python에서 바로 모형을 만들지 않고 C++을 쓴 이유. 발표자료 7쪽은 언어만 적고 있습니다(C++은 알고리듬, Python은 입출력 가공).

직접 돌려 보려면 Gurobi 12와 유효한 라이선스가 있는 Linux가 필요합니다. 학습 목적이라면 6장에서 소개한 roro_model_gurobipy.py로 같은 모형을 만들어 같은 파라미터를 걸어 보는 쪽이 쉽습니다.

이해 확인

모든 경로 비용이 3의 배수인 문제였다면 MIPGapAbs를 얼마로 줄 수 있었을까요?

3 미만, 예를 들어 3 − TOL입니다. 원리는 "목적함수가 가질 수 있는 값들 사이의 최소 간격"보다 작게 주는 것입니다.

N = 300, P = 9인 문제는 어느 쪽으로 가나요?

problemSize = 300 × 9 × 8 / 2 = 10,800 > 10,000이므로 NoRel 쪽입니다. 제한 시간 내내 NoRel 휴리스틱만 돕니다.

NoRel 쪽에서 Heuristics = 0.15는 어떤 영향을 주나요?

영향이 없을 것입니다. Heuristics는 분지한계법이 도는 동안 휴리스틱에 쓰는 비율인데, NoRel이 제한 시간을 다 쓰므로 분지한계법이 시작되지 않습니다.

제한 시간이 60초이고 모형을 만드는 데 1.7초가 걸렸습니다. TimeLimit은 얼마가 되나요?

경과 시간이 초 단위로 버림되어 1이 되므로 60 − 1 − 2 = 57초입니다. 실제 남은 시간은 58.3초이므로 솔버가 57초를 꽉 채우면 해 복원과 Python 쪽 변환에 1.3초가 남습니다.

솔버가 "최적"이라고 선언하고 끝났습니다. 제출된 해가 원래 문제의 최적해라고 말할 수 있나요?

아니요. 모형의 최적해(정확히는 모형 최적값과 2 미만으로 차이 나는 해, 또는 상대 gap 0.01% 이내의 해)입니다. 원래 문제에는 위치변경을 쓰거나 높이를 거스르는, 모형 밖의 더 좋은 해가 있을 수 있습니다.
