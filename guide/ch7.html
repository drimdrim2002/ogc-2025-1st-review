해 복원: 숫자 표를 경로 목록으로

솔버가 끝나면 손에 남는 것은 x, y, z의 값입니다. "항구 1에서 칸 4에 실려 항구 4에서 내려지는 구간이 있다"는 식의 사실들입니다. 대회가 요구하는 것은 항구마다 실행 순서대로 늘어놓은 (경로, 수요 번호) 목록입니다. 이 장은 그 사이를 잇는 코드 get_solution(function.cpp 179~347줄)을 읽습니다.

이 부분에는 최적화가 없습니다. 5장에서 "순서와 경로는 규칙으로 정해진다"고 했던 그 규칙을 그대로 실행하는 절차입니다. 예시는 6장의 최적해를 이어서 씁니다.

1부 · 수요 번호 나눠 주기

getDemandIdVec: (p, q) 주머니에 수요 번호 넣기

항구 쌍 (p, q)마다 주머니를 하나 둡니다. 주머니에는 "이 구간으로 실릴 차의 수요 번호"가 대수만큼 들어갑니다. 코드에서는 demandIdVec[idx2(p, q, num_ports)]라는 정수 벡터입니다.

1단계: 원래 수요를 넣는다. 수요 k가 (o, d), r대이면 주머니 (o, d)에 k를 r번 넣습니다.

// function.cpp 274~284줄
vector<vector<int>> demandIdVec(num_ports * num_ports);          // 주머니 P×P개 (처음엔 모두 빈 벡터)
for (int demand_id = 0; demand_id < num_demands; ++demand_id)
{
    const PortId origin = demand_origin[demand_id];              // K의 demand_id번째 항목의 출발 항구
    const PortId destination = demand_dest[demand_id];           // 도착 항구
    auto& bag = demandIdVec[idx2(origin, destination, num_ports)];
    bag.resize(demand_quantity[demand_id]);                      // 대수만큼 자리를 만들고
    std::fill(bag.begin(), bag.end(), demand_id);                // 전부 수요 번호로 채운다
}

(원래 코드는 bag이라는 이름을 쓰지 않고 demandIdVec[idx2(…)]를 매번 풀어 적습니다. 읽기 쉽게 줄인 것이고 동작은 같습니다.)

2단계: z만큼 쪼갠다. zpqr = n이면 주머니 (p, r)에서 번호 n개를 꺼내, 같은 번호를 주머니 (p, q)와 (q, r)에 하나씩 양쪽 다 넣습니다. 한 대가 두 토막이 되고 두 토막은 같은 수요 번호를 가집니다.

// function.cpp 286~328줄. 줄바꿈과 주석만 손봤다
// (p, q, r) → 아직 못 쪼갠 대수
unordered_map<tuple<PortId, PortId, PortId>, int> remainingSplitAmountMap;
for (PortId p = 0; p < num_ports - 2; ++p)
    for (PortId q = p + 1; q < num_ports - 1; ++q)
        for (PortId r = q + 1; r < num_ports; ++r)
        {
            const int splitAmount =
                std::round(z_pqr[idx3(p, q, r, num_ports, num_ports)].get(GRB_DoubleAttr_X));
            if (splitAmount > 0)
                remainingSplitAmountMap[make_tuple(p, q, r)] = splitAmount;   // 0보다 큰 z만 기록
        }

int num_leftSplit = remainingSplitAmountMap.size();           // 아직 다 못 쪼갠 (p, q, r)의 수
while (num_leftSplit > 0)
    for (auto [key, value] : remainingSplitAmountMap)
    {
        const PortId p = get<0>(key);
        const PortId q = get<1>(key);
        const PortId r = get<2>(key);

        int splitAmount = std::min(value, static_cast<int>(demandIdVec[idx2(p, r, num_ports)].size()));
        if (splitAmount == 0) continue;                       // 주머니 (p, r)이 비어 있으면 다음 바퀴에

        for (int j = 0; j < splitAmount; ++j)
        {
            const int demandId = demandIdVec[idx2(p, r, num_ports)].back();
            demandIdVec[idx2(p, r, num_ports)].pop_back();    // (p, r)에서 번호 하나를 꺼내
            demandIdVec[idx2(p, q, num_ports)].push_back(demandId);   // 앞 토막 주머니와
            demandIdVec[idx2(q, r, num_ports)].push_back(demandId);   // 뒤 토막 주머니에 넣는다
        }
        remainingSplitAmountMap[key] -= splitAmount;
        if (splitAmount == value) --num_leftSplit;            // 이 (p, q, r)은 다 쪼갰다
    }

.get(GRB_DoubleAttr_X)는 Gurobi 변수에서 "솔버가 찾은 가장 좋은 해에서의 값"을 읽는 호출입니다. 값이 실수로 돌아오므로 정수 변수 z는 std::round로 반올림합니다. unordered_map은 해시 맵이라 원소를 도는 순서가 정해져 있지 않습니다.

바깥의 while이 필요한 이유는 두 번 쪼개지는 차 때문입니다. 항구 0 → 4인 차가 항구 2에서 쪼개지고(z024), 뒤 토막 (2, 4)가 항구 3에서 또 쪼개진다면(z234), 주머니 (2, 4)는 첫 번째 쪼개기가 끝나야 채워집니다. 맵을 도는 순서가 정해져 있지 않으므로, 아직 재료가 없는 쪼개기는 건너뛰고 다음 바퀴에 다시 시도합니다. 쪼개기는 항상 긴 구간에서 짧은 구간을 만들기 때문에 서로 물고 물리는 일이 없습니다. 그리고 6장의 제약 ①이 모든 (p, q)에 대해 "들어온 번호의 수 − 쪼개져 나간 번호의 수 = Σi xpqi ≥ 0"을 보장하므로, 가장 긴 구간부터 차례로 따져 보면 어느 쪼개기든 재료가 결국 채워집니다. 그래서 반복은 반드시 끝납니다.

두 번 쪼개지는 경우를 숫자로 보면 이렇습니다. 항구 0 → 4인 수요 7이 1대 있고 z024 = 1, z234 = 1이라고 합시다.

1단계 뒤[7][ ][ ][ ][ ]
(2, 3, 4)를 먼저 시도주머니 (2, 4)가 비어 있어 건너뜀
(0, 2, 4)를 쪼갬[ ][7][7][ ][ ]
다음 바퀴에 (2, 3, 4)를 쪼갬[ ][7][ ][7][7]

이 차는 구간 셋(0 → 2, 2 → 3, 3 → 4)이 되었고 세 주머니에 같은 번호 7이 하나씩 들어 있습니다.

6장의 제약 ①이 보장하는 것은 정확히 "2단계가 끝났을 때 주머니 (p, q)에 든 번호의 수 = Σi xpqi"입니다. 그래서 나중에 구간 하나를 실을 때마다 주머니에서 번호를 하나씩 꺼내면 남지도 모자라지도 않습니다.

주머니에서 어느 번호를 꺼내 어느 칸에 붙이든 채점은 통과합니다. 채점기는 항구를 떠날 때 "수요 k의 차가 배에 몇 대 있는가"만 세기 때문입니다(1장). 수요 k = (o, d)의 번호 하나하나는 쪼개질 때마다 이어진 두 주머니로 나뉘어 들어가므로, 결국 o에서 d까지를 빈틈없이 덮는 구간들의 사슬 하나를 이룹니다. 따라서 o ≤ p < d인 어느 항구 p를 떠날 때든, 번호 k를 달고 배에 실려 있는 차는 정확히 수요 k의 대수만큼입니다.

get_solution의 뼈대

for (PortId currentPortId = 0; currentPortId < num_ports; ++currentPortId)
{
    // ① 머무는 차가 있는 칸 표시
    getAccessibilityInfo(nodeVec, currentPortId, num_nodes, num_ports, x_pqi);

    getBFSOrientation(nodeVec, positionVec);        // ② 남은 그래프에서 BFS

    if (currentPortId > 0)              { /* ③ 하역: 가까운 칸부터 */ }
    if (currentPortId < num_ports - 1)  { /* ④ 선적: 먼 칸부터 */ }

항구를 0번부터 차례로 돌며 네 가지 일을 합니다.

① 머무는 차가 있는 칸을 지운다

// function.cpp 245~272줄 (요지)
if (currentPortId == 0 || currentPortId == num_ports - 1)
    { 모든 노드의 _accessible = true; return; }

for (NodeId i = 1; i < num_nodes; ++i)
{
    bool inaccessibility_found = false;
    for (PortId p = 0; p < currentPortId; ++p)
        for (PortId r = currentPortId + 1; r < num_ports; ++r)
            // 이 항구를 사이에 낀 구간이 있으면
            if (x_pqi[idx3(p, r, i, num_ports, num_nodes)].get(GRB_DoubleAttr_X) > 1 - TOL)
                inaccessibility_found = true;
    nodeVec[i]._accessible = !inaccessibility_found;
}

6장 제약 ②의 왼쪽과 같은 합입니다. 현재 항구보다 전에 실려 뒤에 내려지는 구간이 칸 i에 있으면 그 칸을 _accessible = false로 둡니다. 여기서 두 가지를 눈여겨봅니다.

  • y를 읽지 않습니다. 접근 가능 여부를 x에서 다시 계산합니다. 여기서의 _accessible은 "머무는 차가 없다"는 뜻일 뿐이고, 출입구까지 길이 있는지는 다음 단계의 BFS가 알아냅니다.
  • > 1 - TOL로 비교합니다. 솔버가 돌려주는 값은 실수라서 이진변수도 0.9999999 같은 값으로 올 수 있습니다. TOL = 1e-3이므로 0.999보다 크면 1로 봅니다.

② 남은 그래프에서 다시 BFS

5장에서 본 getBFSOrientation을 다시 부릅니다. 이번에는 _accessible이 false인 칸을 건너뛰므로, 머무는 차가 없는 칸들만으로 이루어진 그래프에서 출입구로부터 BFS를 하는 셈입니다. 결과로 세 가지가 새로 정해집니다.

  • positionVec: 출입구에서 닿을 수 있는 칸들이 가까운 순서로 들어 있는 목록. 닿지 못하는 칸은 목록에 없습니다.
  • _pred: 각 칸에서 출입구 쪽으로 한 걸음 가면 나오는 칸(BFS 트리의 부모).
  • _dist: 머무는 차를 피해서 가는 최단 거리.

경로는 _pred를 따라 출입구까지 거슬러 올라가면 나옵니다.

// function.cpp 333~347줄
vector<NodeId> getUnloadingRoute(vector<Node>& nodeVec, NodeId currentNodeId)
{
    vector<NodeId> unloadingRoute;
    NodeId currentId = currentNodeId;
    while (currentId != 0)
    {
        unloadingRoute.push_back(currentId);
        currentId = nodeVec[currentId]._pred;     // 출입구 쪽으로 한 걸음
    }
    unloadingRoute.push_back(0);
    return unloadingRoute;          // [i, ..., 0] = 하역 경로. 뒤집으면 선적 경로
}

실제 경로는 "모형을 만들 때의 높이"를 따르지 않습니다. 5장의 규칙 ②는 모형이 접근 가능성을 판정할 때 쓴 장치였습니다. 출력 경로는 항구마다 새로 돌린 BFS의 최단 경로입니다. 모형이 "이 칸은 접근 가능하다"고 한 칸에는 높이를 따라 내려가는 빈 길이 적어도 하나 있으므로 BFS가 반드시 그 칸에 닿고, BFS가 찾는 길은 그 길보다 길지 않습니다. 발표자료 3쪽은 "높이가 커지기만(작아지기만) 하는 경로로 적재(하역)한다"고 적고 있지만, 코드가 내놓는 경로는 그보다 짧을 수 있는 최단 경로입니다. 유효성에는 영향이 없습니다.

③ 하역: 가까운 칸부터

// function.cpp 199~218줄
for (int position = 1; position < positionVec.size(); ++position)      // 가까운 칸 → 먼 칸
{
    const NodeId currentNodeId = positionVec[position];
    for (PortId p = 0; p < currentPortId; ++p)
        // 이 항구에서 끝나는 구간이 이 칸에 있으면
        if (x_pqi[idx3(p, currentPortId, currentNodeId, num_ports, num_nodes)]
                .get(GRB_DoubleAttr_X) > 1 - TOL)
        {
            ++portRouteNumVec[currentPortId];
            routeDemandIndexVec.push_back(occupyingDemandIdVec[currentNodeId]);
            vector<NodeId> unloadingRoute = getUnloadingRoute(nodeVec, currentNodeId);
            routeLengthVec.push_back(unloadingRoute.size());
            routeVec.insert(routeVec.end(), unloadingRoute.begin(), unloadingRoute.end());
        }
}

position이 1부터 시작하는 것은 0번이 출입구이기 때문입니다. BFS 순서대로 칸을 훑으면서, 이 항구에서 끝나는 구간이 있는 칸을 만날 때마다 하역 경로를 하나 내보냅니다.

이 순서가 유효한 이유는 5장에서 본 그대로입니다. 어떤 칸의 하역 경로는 _pred를 따라가므로 BFS 순서가 더 앞인 칸들만 지납니다. 그 칸들 중 이 항구에서 내릴 차가 있던 곳은 이미 앞에서 내렸습니다. 머무는 차가 있는 칸은 애초에 BFS에서 빠져 있습니다. 따라서 경로 위에는 차가 없습니다.

④ 선적: 먼 칸부터

// function.cpp 220~241줄
for (int position = positionVec.size() - 1; position > 0; --position)   // 먼 칸 → 가까운 칸
{
    const NodeId currentNodeId = positionVec[position];
    for (PortId r = currentPortId + 1; r < num_ports; ++r)
        // 이 항구에서 시작하는 구간이 이 칸에 있으면
        if (x_pqi[idx3(currentPortId, r, currentNodeId, num_ports, num_nodes)]
                .get(GRB_DoubleAttr_Xn) > 1 - TOL)
        {
            ++portRouteNumVec[currentPortId];
            // 주머니 (현재 항구, r)에서 번호 하나를 꺼낸다
            const int demandId = demandIdVec[idx2(currentPortId, r, num_ports)].back();
            demandIdVec[idx2(currentPortId, r, num_ports)].pop_back();
            routeDemandIndexVec.push_back(demandId);
            vector<NodeId> unloadingRoute = getUnloadingRoute(nodeVec, currentNodeId);
            routeLengthVec.push_back(unloadingRoute.size());
            // 하역 경로를 뒤집어서 넣는다 (rbegin, rend)
            routeVec.insert(routeVec.end(), unloadingRoute.rbegin(), unloadingRoute.rend());
        }
}

하역과 거울상입니다. (값을 읽는 속성 이름이 여기서만 GRB_DoubleAttr_Xn인데, 이 코드에서는 GRB_DoubleAttr_X와 같은 값을 돌려줍니다. 4부에서 설명합니다.) BFS 순서의 뒤에서부터 훑고, 경로는 하역 경로를 뒤집은 [0, …, i]입니다. 수요 번호는 1부에서 만든 주머니 (현재 항구, r)에서 하나 꺼냅니다. 먼 칸부터 채우므로 나중에 싣는 차의 길 위에는 방금 실은 차가 없습니다.

하역을 다 한 다음에 선적을 하므로, 같은 항구에서 차를 내린 칸에 곧바로 다른 차를 실을 수 있습니다. 같은 BFS 결과를 하역과 선적에 함께 써도 되는 이유는, 하역이 끝난 시점에 배에 남은 차가 정확히 "머무는 차"이기 때문입니다.

3부 · C++에서 Python으로

납작한 배열 네 개

대회의 진입점은 Python 함수이고 알고리듬은 C++로 짠 공유 라이브러리 안에 있습니다. Python의 표준 모듈 ctypes가 둘을 이어 줍니다. ctypes로는 정수나 정수 배열 같은 단순한 값만 주고받을 수 있으므로, C++ 함수는 결과를 정수 배열 네 개에 눌러 담아 돌려줍니다(빌드와 호출 방법은 8장). 같은 내용이 세 군데에서 다른 이름으로 불리므로 표로 정리합니다.

입력도 같은 식으로 납작하게 만들어 넘깁니다. Python 쪽에서 입력 K를 둘로 나눕니다.

# myalgorithm.py (입력 변환 부분)
edges_flat = [node for pair in prob_info['E'] for node in pair]     # [[0,1],[1,2]] → [0,1,1,2]

C++ 쪽은 이것을 받아 demand_origin[k], demand_dest[k], demand_quantity[k] 세 벡터로 되돌립니다. 예시의 결과는 출력 배열에 다음과 같이 담깁니다.

out_port_route_num  = [2, 6, 3, 3, 2]                       ← 항구별 경로 개수 (길이 P)
out_demand_indices  = [0,0,  0,0,1,3,0,0,  0,0,2,  0,0,4,  0,0]   ← 경로마다 수요 번호 (하역은 항상 0)
out_route_lengths   = [3,2,  2,3,5,4,3,2,  2,3,2,  2,4,2,  2,5]   ← 경로마다 노드 개수
out_routes          = [0,1,2, 0,1,  1,0, 2,1,0, 0,1,2,3,4, ...]   ← 모든 경로의 노드를 이어 붙인 것

out_route_lengths의 값은 간선 수가 아니라 노드 수입니다(unloadingRoute.size()). myalgorithm.py는 커서 두 개를 움직이며 이것을 다시 자릅니다.

# myalgorithm.py 91~116줄 (요지)
for port_idx in range(num_ports):
    for _ in range(c_out_port_route_num[port_idx]):
        route_len = c_out_route_lengths[route_data_cursor]
        demand_k  = c_out_demand_indices[route_data_cursor]
        route = [c_out_routes[j] for j in range(path_nodes_cursor, path_nodes_cursor + route_len)]
        solution[port_idx].append([route, demand_k])
        path_nodes_cursor += route_len

배열은 Python 쪽에서 미리 넉넉하게 잡아 둡니다. 경로 개수의 상한은 다음 식으로 계산합니다.

max_num_routes = sum(2 * (od_pairs[i][1] - od_pairs[i][0]) * demands[i] for i in range(len(od_pairs)))
max_total_route_len = max_num_routes * num_nodes

예시에서는 2×2×2 + 2×3×1 + 2×1×1 + 2×2×1 + 2×1×1 = 22이고, 실제로 쓰인 경로는 16개입니다. 항구 o에서 d까지 가는 차는 사이의 항구 d − o − 1곳에서 모두 임시로 내려진다 해도 구간이 d − o개이고, 구간 하나에 경로가 둘이므로 차 한 대의 경로는 많아야 2(d − o)개입니다. 5장에서 본 "항구마다 전부 내렸다 다시 싣는" 최악의 해도 이 상한 안에 들어옵니다.

4부 · 코드에서 눈에 띄는 점

하역 경로의 수요 번호는 항상 0이다

③의 코드에서 하역 경로의 수요 번호는 occupyingDemandIdVec[currentNodeId]에서 읽습니다. 이름으로 보면 "그 칸을 차지하고 있는 차의 수요 번호"를 담는 배열입니다. 그런데 이 배열은 선언만 되어 있고(187줄, vector<int> occupyingDemandIdVec(num_nodes);) 값을 써넣는 줄이 코드 어디에도 없습니다. 선적할 때 occupyingDemandIdVec[currentNodeId] = demandId;가 있어야 할 것 같은 자리에 없습니다. 벡터는 0으로 초기화되므로, 제출된 코드는 모든 하역 경로에 수요 번호 0을 붙입니다. 위 배열 예에서 하역 경로 자리가 전부 0인 것이 그 때문입니다.

그런데도 유효해로 채점됩니다. 1장에서 옮겨 본 채점 코드의 하역 부분을 다시 보면 이유가 보입니다.

for route, k in route_list:
    ...
    elif route[-1] == 0:                                # 하역 경로
        unloading_node = route[0]
        if node_allocations[unloading_node] == -1:      → 무효 (내릴 차가 없음)
        for i in route[1:]:
            if node_allocations[i] != -1:               → 무효 (길이 막힘)
        node_allocations[unloading_node] = -1           # 칸을 비운다. k는 어디에도 쓰이지 않는다

주최 측 util.py의 check_feasibility는 하역 경로를 처리할 때 수요 번호 k를 보지 않습니다. 첫 노드에 차가 있는지, 나머지 노드가 비었는지, 간선이 있는지만 확인하고 그 칸을 비웁니다. 수요 번호는 선적 경로에서만 쓰이고(그 칸에 어느 수요의 차가 놓였는지 기록), 항구를 떠날 때 배에 있는 차의 수요별 대수를 세는 데 쓰입니다.

의도한 생략인지 빠뜨린 것인지는 코드만으로는 알 수 없습니다. 어느 쪽이든 대회의 채점 규칙 아래에서는 결과에 영향이 없습니다. 이 코드를 다른 곳에 가져다 쓰면서 하역 경로의 수요 번호가 필요하다면 한 줄을 채워 넣어야 합니다.

그 밖의 관찰

  • X와 Xn이 섞여 있습니다. 하역과 접근 가능 계산은 GRB_DoubleAttr_X를, 선적은 GRB_DoubleAttr_Xn을 읽습니다. X는 가장 좋은 해의 값입니다. Gurobi는 탐색 중에 찾은 해를 몇 개까지 보관해 두는데(이 목록을 해 풀, solution pool이라고 합니다), Xn은 그 목록에서 SolutionNumber번째 해의 값입니다. SolutionNumber의 기본값이 0(가장 좋은 해)이고 코드가 이 값을 바꾸지 않으므로 둘은 같은 값을 돌려줍니다(Gurobi 12 문서의 Xn 항목). 동작에는 차이가 없습니다.
  • 해가 있는지 확인하지 않습니다. model.optimize() 뒤에 상태나 해의 개수를 검사하는 코드가 없습니다. 솔버가 제한 시간 안에 가능해를 하나도 못 찾았다면 .get(GRB_DoubleAttr_X)에서 Gurobi가 예외를 던지는데, 이를 받는 try/catch도 없습니다. 그 경우 프로그램은 비정상 종료할 것으로 보입니다(실행해 확인하지는 않았습니다). 대회 결과에 tryAgain의 crash나 infeasible 기록은 없으므로 실제로는 일어나지 않았습니다.
  • 같은 (출발, 도착) 쌍의 수요는 하나뿐이라고 가정합니다. 수요 표를 만들 때 demandQuantityVec[idx2(p, q)] = …로 덮어쓰고, 주머니도 resize와 fill로 덮어씁니다. 입력 K에 같은 쌍이 두 번 나오면 뒤의 것만 남습니다. 문제 설명이 이를 명시적으로 보장하지는 않지만, 대회 문제에서는 문제가 되지 않았습니다.
  • 쓰이지 않는 인자가 있습니다. get_solution은 y_pi와 fixed_cost를 받지만 쓰지 않습니다. 복원에 필요한 것은 x와 z뿐입니다.
  • z는 반올림해서 읽습니다. std::round(z.get(GRB_DoubleAttr_X)). 정수 변수도 실수로 돌아오기 때문입니다.

이해 확인

항구 2에서 BFS로 닿는 칸이 1, 2뿐인 이유는 무엇인가요?

칸 3(x133)과 칸 4(x144)에 항구 2를 사이에 낀 구간, 즉 머무는 차가 있어서 _accessible이 false이기 때문입니다. 일렬 배에서 칸 3이 빠지면 그 너머의 칸 4도 어차피 닿을 수 없습니다.

하역을 먼 칸부터 하면 어떤 일이 생기나요?

먼 칸의 차가 나가는 길 위에, 아직 내리지 않은 가까운 칸의 차가 있을 수 있습니다. 그 경로는 무효입니다. 예시의 항구 1에서 [2,1,0]을 [1,0]보다 먼저 실행하면 칸 1의 차에 막힙니다.

임시로 내린 차와 다시 실은 차가 "같은 차"라는 것은 출력의 어디에 나타나나요?

재적재 선적 경로의 수요 번호에 나타납니다. getDemandIdVec이 쪼갠 두 토막의 주머니에 같은 수요 번호를 넣었기 때문에, 다시 싣는 경로가 원래 수요 번호를 달고 나옵니다. 하역 경로 쪽의 번호는 채점에 쓰이지 않습니다.

모형의 목적함수 값과 채점기가 계산한 총비용이 다를 수 있는 경우는 언제인가요?

배에 홀수 길이의 순환이 있고, 어떤 칸의 "거리가 1 작은 이웃"이 모두 머무는 차로 막혀 같은 거리의 이웃을 거쳐 돌아가야 하는 경우입니다. 이때 실제 경로가 dist(i)보다 길어져 채점기의 비용이 더 큽니다(6장).

out_route_lengths의 합은 무엇과 같아야 하나요?

out_routes에 실제로 채워진 원소의 수입니다. 예시에서는 3+2+2+3+5+4+3+2+2+3+2+2+4+2+2+5 = 46입니다. 간선 수의 합은 여기서 경로 수 16을 뺀 30이고, 총비용은 16 × 10 + 30 = 190입니다.
